A Layer-1 for transfers, final in one block. Блокчейн для переводов с финальностью в один блок.

Phylox is an independent Layer-1 written from scratch in Go. Tendermint-style BFT consensus produces a block every 4 seconds; once two thirds of the validators sign it, the transfer cannot be reversed. The base fee is 0.0001 YLX, and half of every fee is burned.

Phylox — самостоятельный блокчейн первого уровня, написанный с нуля на Go. BFT-консенсус в духе Tendermint выпускает блок раз в 4 секунды; как только блок подписали две трети валидаторов, перевод уже не откатить. Базовая комиссия — 0,0001 YLX, половина каждой комиссии сжигается.

How it worksКак устроено

Phylox does one thing — moves value between accounts — and keeps every part of that path small enough to reason about. Each decision has a written record with its trade-offs and known weak points.

Phylox делает одно — переводит ценность между аккаунтами — и держит каждую часть этого пути достаточно простой, чтобы о ней можно было рассуждать. У каждого решения есть запись с ценой выбора и известными слабыми местами.

BFT consensus, built from scratchBFT-консенсус, написанный с нуля

A Tendermint-style protocol implemented in Go rather than taken from CometBFT. A proposer chosen in turn offers a block; validators prevote, then precommit, and ⌈2n/3⌉ precommits decide it.

Протокол в духе Tendermint, реализованный на Go, а не взятый из CometBFT. Сборщик по очереди предлагает блок; валидаторы голосуют предварительно, затем окончательно, и ⌈2n/3⌉ окончательных голосов решают его судьбу.

  • Locking and proof-of-lock rules keep safety across rounds
  • Timeouts: proposal 3 s + 0.5 s per round, votes 1 s + 0.5 s
  • On-disk guard refuses to sign twice at the same height and round
  • Блокировка и доказательство блокировки сохраняют безопасность между раундами
  • Сроки: предложение 3 с + 0,5 с на раунд, голоса 1 с + 0,5 с
  • Защита на диске не даёт подписать дважды на одной высоте и раунде

SPEC §6 · ADR-0031

Final in one blockОкончательно за один блок

Any two quorums of two thirds share at least one honest validator, so two different blocks at the same height cannot both be decided. There are no forks to wait out: a transfer is final when its block is.

Два кворума по две трети всегда пересекаются хотя бы в одном честном валидаторе, поэтому два разных блока на одной высоте решены быть не могут. Ждать подтверждений не нужно: перевод окончателен вместе со своим блоком.

  • Every block carries the commit of its parent
  • No block is executed before its commit is verified, including blocks received during sync
  • The chain keeps going with three of four validators online
  • Каждый блок несёт коммит своего родителя
  • Ни один блок не исполняется до проверки коммита — и при синхронизации тоже
  • Сеть продолжает работу при трёх валидаторах из четырёх

SPEC §5–6 · ADR-0031

State with Merkle proofsСостояние с доказательствами Меркла

Accounts hold balances and nonces. State is stored flat in Pebble for one-read lookups and committed to a binary sparse Merkle tree whose root is in every block header.

Аккаунты хранят баланс и счётчик. Состояние лежит в Pebble плоско — одно чтение на запрос — и фиксируется двоичным разреженным деревом Меркла, корень которого есть в каждом заголовке.

  • Proofs of inclusion and of absence
  • Transactions committed by a Merkle root, with their count under the header hash
  • A block applies atomically, or not at all
  • Доказательства наличия и отсутствия
  • Транзакции заверены корнем Меркла, их число — под хешем заголовка
  • Блок применяется целиком или не применяется вовсе

SPEC §5, §8 · ADR-0020

Issuance and fee burnЭмиссия и сжигание

Every node computes the block reward from the block height with integer arithmetic, rounding down. A validator cannot write its own reward into a block.

Каждый узел вычисляет награду из высоты блока целочисленно, с округлением вниз. Валидатор не может вписать себе награду в блок.

  • 10% to the proposer, 90% to the signers of the parent commit
  • Half of every fee is burned, so net issuance shrinks as usage grows
  • The new-account surcharge is burned in full
  • 10% сборщику, 90% подписавшим коммит родителя
  • Половина каждой комиссии сгорает: чем больше переводов, тем меньше чистый прирост предложения
  • Доплата за новый адрес сгорает целиком

SPEC §7 · ADR-0007

Validator set in chain stateСостав валидаторов в состоянии сети

Membership is part of the state, not a configuration file. Each validator has an owner: a separate cold address that receives rewards and votes on who joins or leaves.

Состав — часть состояния сети, а не файл настроек. У каждого валидатора есть владелец: отдельный холодный адрес, который получает награды и голосует, кого включить или исключить.

  • Add, remove or change owner by a two-thirds vote of owners
  • The node key holds no funds
  • Evidence of a double vote removes a validator at the next height
  • Включение, исключение и смена владельца — голосованием двух третей владельцев
  • Ключ узла денег не держит
  • Доказательство двойного голоса исключает валидатора со следующей высоты

SPEC §6 · ADR-0031

Network and keysСеть и ключи

Peers connect over TCP with a Noise XX handshake bound to the chain ID and genesis. A node listens only on 127.0.0.1 until its operator opens it, so the operator’s IP is not announced by default.

Узлы соединяются по TCP через рукопожатие Noise XX, привязанное к номеру сети и генезису. Пока оператор сам не откроет узел, тот слушает только 127.0.0.1, и IP оператора в сеть не уходит.

  • Peer scoring and bans by key and IP
  • Wallet keystore: Argon2id + XChaCha20-Poly1305; the key never leaves the wallet
  • Node RPC on loopback only, with a fresh token on every start
  • Штрафные очки и баны по ключу и IP
  • Хранилище ключа: Argon2id + XChaCha20-Poly1305; ключ не покидает кошелёк
  • RPC узла — только на loopback, с новым токеном при каждом запуске

SPEC §9–11 · ADR-0026, ADR-0027

Life of a transferПуть перевода

  1. WalletКошелёк

    SignПодпись

    The wallet signs locally: a native transfer, or a legacy Ethereum (EIP-155) transfer from MetaMask.

    Кошелёк подписывает у себя: родной перевод или перевод Ethereum (legacy, EIP-155) из MetaMask.

  2. MempoolОчередь

    AdmitПриём

    Form, validity window, fee, signature, nonce and balance are checked before the transaction takes any space.

    Форма, окно жизни, комиссия, подпись, счётчик и баланс проверяются до того, как транзакция займёт место.

  3. ProposerСборщик

    ProposeПредложение

    Up to 256 KiB of transactions, each dry-run against the state, so the offered block is valid.

    До 256 КиБ транзакций, каждая прогнана по состоянию заранее, поэтому предложенный блок годен.

  4. ValidatorsВалидаторы

    DecideРешение

    Prevote, then precommit. ⌈2n/3⌉ precommits decide the block, and it is final.

    Предварительный голос, затем окончательный. ⌈2n/3⌉ окончательных голосов решают блок — он окончателен.

  5. Every nodeКаждый узел

    CommitЗапись

    State changes are written atomically with the new state root; the commit signatures travel in the next block.

    Изменения состояния записываются одной пачкой с новым корнем; подписи коммита уходят в следующий блок.

In practice a transfer lands in a block within 4–8 seconds and is final immediately.На практике перевод попадает в блок за 4–8 секунд и сразу становится окончательным.

The source code is not public yet; it opens with the public testnet. This is what the interfaces look like today. There is no public RPC endpoint: the addresses below belong to a node you run yourself.

Node and walletУзел и кошелёк

phyloxd runs a validator (with a key) or an observer. phylox-cli manages encrypted keystores, sends transfers, looks up transactions and votes on the validator set. Release builds for Linux (amd64, arm64) and Windows (amd64).

phyloxd работает валидатором (с ключом) или наблюдателем. phylox-cli ведёт зашифрованные хранилища ключей, отправляет переводы, показывает транзакции и голосует за состав валидаторов. Сборки для Linux (amd64, arm64) и Windows (amd64).

JSON-RPC

JSON-RPC 2.0 over HTTP, loopback only, with a bearer token the node writes to rpc.cookie on every start. Methods include phylox_status, phylox_getAccount, phylox_sendRawTransaction, phylox_getBlockByHeight, phylox_getValidators and phylox_consensus.

JSON-RPC 2.0 поверх HTTP, только loopback, с токеном, который узел пишет в rpc.cookie при каждом запуске. Среди методов — phylox_status, phylox_getAccount, phylox_sendRawTransaction, phylox_getBlockByHeight, phylox_getValidators и phylox_consensus.

MetaMask and Ethereum librariesMetaMask и библиотеки Ethereum

An optional eth_* endpoint lets MetaMask, ethers and similar tools send YLX. The wallet signs an ordinary legacy (EIP-155) transfer; no Snap or plugin is needed. The endpoint is read-only apart from submitting signed transfers.

Необязательный эндпоинт eth_* позволяет MetaMask, ethers и похожим инструментам переводить YLX. Кошелёк подписывает обычный перевод legacy (EIP-155); Snap и дополнения не нужны. Кроме отправки подписанных переводов, эндпоинт только читает.

ExplorerОбозреватель

A separate read-only program indexes blocks, transactions and address history from a node over RPC and serves plain HTML pages, with no JavaScript and no external resources.

Отдельная программа только для чтения: строит индекс блоков, транзакций и истории адресов по RPC узла и отдаёт простые HTML-страницы — без JavaScript и внешних ресурсов.
